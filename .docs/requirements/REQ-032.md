# REQ-032: Puente opcional StrictDoc para el Pilar 1

> v1.0 (2026-10-01): orden del programador — complementar el proyecto con
> StrictDoc (requisitos en texto plano, diagramas Mermaid, bloques de
> pseudocódigo, colaboración asíncrona vía Git). Decisión en ADR-011.
> Datos del prototipo aislado (P1.21, `/tmp/sdoc-demo`, strictdoc 0.30.1):
> instalación 444 MB (~100 paquetes transitivos), pip-audit **0
> vulnerabilidades** (2026-10-01), export de 1 documento en ~1.6 s con 4 vistas
> HTML (17 MB estáticos), diagrama Mermaid renderizado como
> `<pre class="mermaid">` (render local en el navegador: el texto no sale del
> equipo).

## Objetivo

Complementar el Pilar 1 con documentos StrictDoc (`.sdoc`: requisitos con UID,
Mermaid/PlantUML, pseudocódigo) **sin migrar** los `REQ-XXX.md` existentes:
trazabilidad `.sdoc` ↔ código validada por `scripts/strictdoc_bridge.py`
(stdlib, sin strictdoc instalado); la capa pesada (strictdoc para exportar
HTML) queda opcional y aislada, coherente con el diseño stdlib-first.

## Criterios de aceptacion

1. `requirements-strictdoc.txt`: strictdoc fijado (`==0.30.1`) con notas de
   instalación aislada (venv o `pip --target`, P0.5) y de la auditoría
   P0.18 ejecutada (pip-audit 0 vulns, evidencia en PRUEBAS ronda 38).
2. `scripts/strictdoc_bridge.py` (solo stdlib): localiza `.sdoc` en
   `.docs/requirements/` (recursivo; `--root` para externos) y valida:
   (a) documentos parseables (nodos y campos mínimos),
   (b) UIDs únicos en todos los `.sdoc`,
   (c) todo `[REQUIREMENT]` con `UID` y `TITLE` o `STATEMENT`,
   (d) toda referencia `SDOC-XXX` en código existe como UID en algún `.sdoc`.
   Salida 0 verde / 1 rojo; `--json` para máquina.
3. Esquema de UIDs `SDOC-\d{3}` (sin subcadena `REQ-\d{3}`): evita colisiones
   con `CODE_RE` de `doc_validator.py` (`\bREQ-(\d{3})\b`), verificado con
   test dedicado — los `.sdoc` no contaminan la trazabilidad clásica.
4. Dogfooding: `.docs/requirements/puente-strictdoc.sdoc` real (SDOC-001,
   SDOC-002 + diagrama Mermaid), referenciado desde el bridge (`# SDOC-001`);
   `strictdoc export` verificado en el prototipo antes de integrar (P1.21).
5. Verificador (paridad bash/Python): check `trazabilidad StrictDoc (.sdoc)`
   que ejecuta el bridge si hay `.sdoc` y emite `[SKIP]` si no los hay.
6. Tests en `tests/test_strictdoc_bridge.py` con casos límite que PUEDEN
   fallar (P1.1): UID duplicado, requisito sin UID, sin TITLE/STATEMENT,
   referencia de código a UID inexistente, `>>>` sin cerrar, no colisión
   `REQ-\d{3}`, modo `--root` externo y `--json`.
7. Documentación: ADR-011, README (capa opcional), HERRAMIENTAS-Y-FUENTES
   (strictdoc, Apache-2.0, 444 MB), PRUEBAS ronda 38 (evidencia real).
8. Núcleo intacto: suite y verificador pasan SIN strictdoc instalado; ninguna
   dependencia nueva para el núcleo.

## Fuera de alcance

- Migrar `REQ-XXX.md` a `.sdoc` (el Markdown clásico sigue siendo la autoridad
  de trazabilidad; ADR-011).
- Servidor web de strictdoc en CI o como servicio (uso local puntual).
- Edición de requisitos vía la web UI de strictdoc.
