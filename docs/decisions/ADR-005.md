# ADR-0001: Proposito del proyecto

## Contexto
El proyecto `better-project` nacio como ecosistema local de gestion: requisitos, conocimiento, lecciones y control de sesgos viven en el repo como archivos; Git es el versionado; los scripts de `scripts/` son las herramientas; los agentes de IA las consumen via reglas (`AGENTS.md`) y MCP local.

La ambigüedad entre "producto" (aplicacion para usuarios finales) y "meta-proyecto" (framework para gobernar proyectos con agentes) ha llevado a evaluaciones invalidas (p.ej. 96/100 sin definir que se mide) y a decisiones de alcance poco claras (demo con 3 REQs vs tooling de 10 scripts).

## Alternativas consideradas
1. **Producto CLI** - Enfocar en `demo/notas.py` como aplicacion principal, tooling como soporte
2. **Meta-proyecto** - Enfocar en el framework de verificacion, trazabilidad y gobernanza; demo como ejemplo minimo
3. **Hibrido** - Mantener ambos con igual peso

## Decision
**better-project es un meta-proyecto (framework metodologico).**

El proposito principal es proporcionar un **framework de gobernanza para proyectos asistidos por IA** que garantice:
- Trazabilidad bidireccional REQ <-> codigo
- Conocimiento versionado y consultable
- Lecciones aprendidas sistematicas
- Control de sesgos y falacias en decisiones
- Verificacion ejecutable y determinista
- MCP local para agentes

La demo (`demo/`) es un **proyecto de ejemplo minimo** que valida el framework, no el producto principal.

## Consecuencias
### Positivas
- Claridad absoluta para priorizacion: tooling > demo
- KPIs del framework tienen sentido (O23)
- No hay presion para "features de usuario" en la demo
- El 35:1 ratio tooling/producto es una feature, no un bug

### Negativas / Riesgos
- Riesgo: tooling crece sin control (mitigado por O10, O11)
- Riesgo: demo no valida escalabilidad (mitigado por O14)
- Riesgo: usuarios esperan "producto" (mitigado: README claro)

## Supuestos
- El valor esta en la **metodologia**, no en la aplicacion de ejemplo
- Los agentes (opencode, kilocode) son los consumidores principales
- La verificacion ejecutable es el corazon del sistema

## Metricas de exito
- 100% REQs coherentes con proposito meta-proyecto
- KPIs del framework (O23) definidos y medidos
- Demo valida framework con >= 20 REQs (O14)
